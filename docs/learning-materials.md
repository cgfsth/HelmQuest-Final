# Learning materials

This feature adds academic PDF documents to the existing portals. Students open **Learning Materials**; instructors and administrators open **Syllabus Management**. All roles use the same library component. It does not use or change simulation `training_modules`, missions, quizzes, scores or onboarding.

## Runtime and configuration

Run `npm ci` and `npm run build` at the project root. Run `npm ci` in `backend` and start its existing server. The existing `VITE_API_BASE_URL` must point to that server's `/api/v1` endpoint. Node 22.13+ or Node 24+ is required by the installed PDF.js release.

The backend uses the existing Firebase Admin service account and project. Set `FIREBASE_STORAGE_BUCKET=helmquest-565d6.firebasestorage.app` (the default matches the existing client config). The bucket must be provisioned in this project and the service account must have Firestore and Storage object read/create/delete/list permissions. Keep the bucket private: no `allUsers`/`allAuthenticatedUsers` object access or public object ACLs on protected material paths. No signed URL, Firebase download token or permanent public URL is generated by this feature. This implementation does not provision a bucket or change billing/IAM automatically.

Existing student/instructor sign-in already receives a signed, 12-hour server session. The existing local admin login stays unchanged; opening this feature verifies its in-memory login credentials against `/auth/demo-login` to obtain the same server session. Tokens and passwords are not added to localStorage or PDF URLs. Set a stable `AUTH_SESSION_SECRET` on the backend if sessions should survive restarts. Client role props control presentation only; every API request verifies the signature, current account status and current instructor assignment. Pending/rejected/inactive accounts are denied.

## Security rules: required before production

The repository did not contain the deployed project's complete Firestore or Storage rules. Two **merge fragments** are included in `firebase/learning-materials.firestore.rules` and `firebase/learning-materials.storage.rules`. They deny all direct Firebase client access to the two new namespaces, including subcollections; the authenticated API is the only document access path. Its Admin SDK is authorized independently of those rules.

Merge these fragments into the existing rules; retain all unrelated restrictions. Firebase matching `allow` expressions are additive: a broad existing `match /{document=**}` or `match /{path=**}` allow would override a feature-only deny. Such allows must explicitly exclude the first path segment `syllabi` and `syllabus_modules`. For example, restructure a broad allow as `match /{collection}/{rest=**}` with `allow ...: if collection != 'syllabi' && collection != 'syllabus_modules' && EXISTING_CONDITION;`. Review every overlapping allow, including recursive matches. Apply equivalent exclusions to Storage paths. Do not weaken `EXISTING_CONDITION` or replace the full rules with these fragments. There is intentionally no new `firebase.json` that could accidentally deploy incomplete rules over existing functionality.

Verify direct client/anonymous metadata reads, writes and file downloads are denied, while authorized API reads work, in staging before production. Rule merging and deployment require approval; neither has been performed by this change. Backend tests use in-memory Firebase substitutes and do not claim to verify currently deployed Firebase rules or live bucket IAM.

## Data

Only two new Firestore collections are written:

| Collection | Fields |
| --- | --- |
| `syllabi` | title, description, instructorId, createdBy, fileName, fileSize, contentType, storagePath, moduleCount, createdAt, updatedAt, revision, status, pendingFileDeletes |
| `syllabus_modules` | syllabusId, title, description, moduleNumber, uploadedBy, fileName, fileSize, contentType, storagePath, createdAt, updatedAt, revision, status, pendingFileDeletes |

Firestore `doc()` generates IDs; creation/update times use `FieldValue.serverTimestamp()`. Storage contains the actual bytes at `syllabi/{id}/{uuid}.pdf` or `syllabus_modules/{id}/{uuid}.pdf`. The first successful upload/metadata commit creates each collection automatically. Existing blank `title: ""` placeholders are ignored and left untouched. No migration or manual placeholder creation is needed.

Instructors manage records with their `instructorId`. Administrators assign/reassign syllabi to active instructors. Student scope comes from the freshly loaded student record's `instructorid`/`instructorId`; every module inherits its current parent's scope. Reassignment therefore also moves all child access. Queries use a single instructor equality or parent equality, then sort module numbers in memory; no composite index is needed. A syllabus supports up to 200 modules; module numbers are unique integers 1–999. Reorder arrows atomically renumber the active set from 1. Parent revisions serialize child changes with deletion and reassignment.

## Files, failures and retries

PDFs are limited to 15 MiB, one file per request, with extension, MIME, `%PDF-` signature and terminal `%%EOF` validation. These checks reject common invalid uploads; full PDF parsing occurs in the reader, which reports corrupt/password-protected documents. Upload concurrency and parser limits bound memory use. The UI shows byte upload progress, then a saving state until the backend commits metadata.

Replacement uploads a new unique private object, commits its metadata transactionally, and only then deletes obsolete objects. A stale revision returns 409. Failed pre-commit work attempts to remove the staged object. Failed old-file cleanup stays in `pendingFileDeletes`; the newly committed PDF remains readable. Deletion first hides the record using a durable `deleting` status and then removes files and the tombstone. Failed deletions remain retryable. Syllabus deletion is blocked while any module record remains, including pending deletion, preventing orphaned children. The UI has a **Retry cleanup** action for managers.

After a network timeout/lost response, refresh before retrying an upload: the server may already have committed. There is no automatic replay of create requests. Run `npm run cleanup:materials` from `backend` as a daily scheduled task with the same private service account. It retries durable queues and removes unreferenced objects older than 24 hours, scanning only these two prefixes. This catches a process crash between upload and metadata commit (including failures where immediate cleanup cannot reach Storage). Objects referenced by current metadata or pending queues are retained. Scheduling that task is a hosting configuration step; it is not installed automatically.

The reader retrieves authorized PDF bytes through Bearer-authenticated requests with private/no-store responses. PDF.js, its worker, fonts, CMaps and image decoders are bundled/served from the frontend origin. Pages render lazily near the viewport and release offscreen canvases. Text is selectable and available to assistive technology; scanned image-only documents need an accessible source PDF from the instructor. Controls include scrolling, page navigation, fit width and zoom. Browser viewing does not prevent saving or screenshots.

## API

All paths below are relative to `/api/v1/learning-materials`; all require the signed session.

| Method | Path | Access |
| --- | --- | --- |
| GET | `/syllabi?search=&instructorId=` | Scoped reads; instructor filter is admin-only |
| GET | `/syllabi/:id` | Accessible syllabus and sorted modules |
| GET | `/instructors` | Managers; admin sees active assignment choices |
| POST | `/syllabi` | Managers; multipart fields + PDF |
| PUT | `/syllabi/:id` | Scoped managers; multipart fields, revision, optional replacement |
| POST | `/syllabi/:id/modules` | Scoped managers; multipart fields + PDF |
| PUT | `/modules/:id` | Scoped managers; multipart fields, revision, optional replacement |
| DELETE | `/syllabi/:id`, `/modules/:id` | Scoped managers; JSON revision |
| POST | `/syllabi/:id/reorder` | Scoped managers; JSON revision and ordered ids |
| GET | `/syllabi/:id/pdf`, `/modules/:id/pdf` | Same scope as parent; PDF bytes |
| POST | `/cleanup` | Retry cleanup within manager's scope |

## Validation

- `npm run test:materials` at the project root: browser-independent API and integration checks.
- `npm run test:materials` in `backend`: real Express/multer HTTP requests with isolated fake Firestore/Storage; ownership, roles, data validation, concurrency, replacement/deletion failures and cleanup.
- `npm run verify:materials` at the root: hidden Edge with the actual Vue component, API, upload parser and PDF.js, using local synthetic records/files. Screenshots go outside the repo to `../.tmp/learning-materials-verification`.
- `node --test tests/*.test.mjs` at the root: existing regression tests.
- `npm run build`: production compilation and local PDF assets.

No production data, security rules, deployment or GitHub branch is changed by these validation commands.
